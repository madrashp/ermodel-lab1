# design-decisions.md — Пояснення ключових рішень моделювання

## Рішення #1: UserMembership як асоціативна сутність

### Питання
Чи UserMembership є просто об'єднувальною таблицею (junction table) для зв'язку M:M між User та Membership, чи це повноцінна сутність?

### Рішення
**UserMembership є повноцінною асоціативною сутністю**, а не простою з'єднувальною таблицею.

### Обґрунтування

1. **Власні атрибути:**
   - UserMembership несе власний семантичний зміст: `start_date`, `end_date`, `is_active`
   - Ці атрибути описують період дії членства, не залежать від User чи Membership окремо
   - Це критерій асоціативної сутності за Чен (E-R модель)

2. **Історія змін:**
   - Один користувач може мати кілька членств послідовно (змінювати пакет)
   - Кожне членство — окремий період дії з власною датою початку/закінчення
   - Приклад:
     ```
     User #1 "John"
       → Membership: Basic (2024-01-01 до 2024-06-30)
       → Membership: Pro   (2024-07-01 до 2024-12-31)
       → Membership: Pro   (2025-01-01 до 2025-06-30)
     ```

3. **Платежі залежать від членства:**
   - Payment FK посилається на user_membership_id, не на (user_id + membership_id)
   - Це тому, що платежі мають бути пов'язані з конкретним періодом членства
   - Один користувач на одну дату платить за одне членство, але в різні періоди — за різні членства

4. **Порівняння з простою junction table:**
   - **Проста junction table** (без власних атрибутів):
     ```sql
     CREATE TABLE user_membership (
       user_id INT FK,
       membership_id INT FK,
       PRIMARY KEY (user_id, membership_id)
     );
     ```
     Цей вибір був би неправильним, бо не дозволяє історію змін.

   - **Асоціативна сутність** (з власними атрибутами):
     ```sql
     CREATE TABLE user_membership (
       user_membership_id INT PK,
       user_id INT FK,
       membership_id INT FK,
       start_date DATE,
       end_date DATE,
       is_active BOOLEAN
     );
     ```
     Це дозволяє історію, періоди дії, і правильне моделювання платежів.

### Висновок
UserMembership — **асоціативна сутність**, а не простий junction table, тому має окремий PK (user_membership_id) та власні атрибути.

## Рішення #2: Booking — бізнес-правило про неперекриття

### Питання
Як забезпечити, щоб один простір не був заброньований з перекриваючими часовими інтервалами?

### Рішення
**Бронювання не можуть перекриватися** на один простір та дату — це бізнес-правило, а не структурне обмеження на рівні ER-моделі.

### Обґрунтування

1. **Бізнес-правило:**
   - Один простір може одночасно використовуватися лише однією групою
   - Два бронювання для одного простору конфліктують, якщо їхні часові інтервали мають спільні точки

2. **Чому UNIQUE недостатня:**
   - UNIQUE(space_id, booking_date, start_time) забороняє лише два бронювання з однаковим start_time
   - Але дозволить перекриття: Booking A (10:00–12:00) і Booking B (11:00–13:00) мають різні start_time, однак перекриваються
   - Приклад неправильного дозволу:
     ```
     Booking 1: space=5, date=10.10, start_time=10:00, end_time=12:00
     Booking 2: space=5, date=10.10, start_time=11:00, end_time=13:00
     
     UNIQUE(space_id, booking_date, start_time) дозволив би обидва записи,
     але інтервали перекриваються (11:00–12:00).
     ```

3. **На рівні ER-моделі:**
   - Бізнес-правило позначається як примітка до сутності Booking
   - Структура бази даних (PK, FK, типи) залишається незмінною

4. **На рівні реалізації (поза ER-моделлю):**
   - Перевірка реалізується в прикладному коді перед вставкою/оновленням
   - Або через тригер БД (якщо СУБД підтримує перевірку перекриття часових інтервалів)
   - Логіка: `NOT EXISTS(SELECT 1 FROM booking WHERE space_id = new.space_id AND booking_date = new.booking_date AND (start_time, end_time) OVERLAPS (new.start_time, new.end_time))`

### Висновок
Бізнес-правило "неперекриття" визначено у spec.md, але не вводить змін у структуру ER-моделі. Перевірка — справа прикладної логіки, не DDL.

## Рішення #3: Payment — чому FK на user_membership_id, а не на booking_id

### Питання
Платежі мають бути прив'язані до бронювань чи до членств?

### Рішення
**Payment FK посилається на user_membership_id**, не на booking_id.

### Обґрунтування

1. **Бізнес-модель коворкінгу:**
   - Користувачі платять за **членство** (пакет), не за окремі бронювання
   - Членство включає кількість годин на місяць (max_hours_per_month)
   - Бронювання — це використання цих годин
   - Приклад:
     - Pro членство коштує 500 грн/місяць і включає 40 годин
     - Користувач робить кілька бронювань (дом, офіс, конференц-зала)
     - За весь місяць він платить один раз за членство

2. **Альтернативи:**
   - ❌ Payment → Booking: Неправильно, бо один платіж мав би бути за весь місяць, а не за кожне бронювання
   - ✅ Payment → UserMembership: Правильно, бо платіж покриває весь період членства

3. **Практичний приклад:**
   ```
   UserMembership: Pro package (2024-11-01 to 2024-11-30)
   ├─ Payment: 500 грн (2024-11-01) ← ONE платіж за місяць
   └─ Bookings:
      ├─ Booking #1: Mon 04-Nov, 09:00-11:00
      ├─ Booking #2: Wed 06-Nov, 14:00-16:00
      ├─ Booking #3: Fri 08-Nov, 10:00-12:00
   ```

### Висновок
Payment правильно FK на user_membership_id, що відповідає бізнес-логіці членства.

## Рішення #4: Review — чому є окрема сутність

### Питання
Чи Review мав би бути частиною Booking, чи окремою сутністю?

### Рішення
**Review — окремена сутність**, FK на User та Space.

### Обґрунтування

1. **Кардинальність:**
   - Бронювання 1:1 з Review? Ні, бо не всі бронювання отримують оцінку
   - Review 1:M з Booking? Можливо, але неправильно
   - User 1:M Review? Правильно — один користувач може оцінити багато просторів
   - Space 1:M Review? Правильно — один простір отримує багато оцінок

2. **Семантика:**
   - Review оцінює не саме бронювання, а сам простір (Space)
   - Користувач може залишити одну оцінку за простір, навіть якщо бронював його кілька разів
   - Оцінка залежить від впечатлення від простору, а не від конкретного часу бронювання

3. **Приклад:**
   ```
   User "John" → Reviews:
   ├─ Space "Conference Room A": ⭐⭐⭐⭐⭐ "Відмінна кімната!"
   ├─ Space "Hot Desk Area": ⭐⭐⭐ "Шумно, але зручно"
   ```

### Висновок
Review — окремена сутність FK на User та Space, що дозволяє правильне моделювання оцінок просторів.

## Рішення #5: Нормалізація до 3NF

### Чому 3NF, а не BCNF або денормалізація?

1. **3NF достатня:**
   - Усі сутності в моделі нормалізовані до 3NF
   - BCNF надмірна для цього домену
   - Денормалізація непотрібна для цієї простої моделі

2. **Преваги 3NF:**
   - Мінімізація дублювання даних
   - Простота оновлень
   - Відсутність аномалій вставлення/видалення
   - Компактна схема

3. **Приклад нормалізації User:**
   - ✅ 1NF: email, full_name, phone — атомарні значення
   - ✅ 2NF: всі атрибути залежать від повного PK (user_id)
   - ✅ 3NF: немає перехідних залежностей (напр., "email → домен компанії")

## Альтернативні рішення, що розглядались, але відхилені

| Альтернатива | Причина відхилення |
|-------------|-------------------|
| Booking FK на Membership замість на Space | Бронювання — це резервування простору, не членства |
| Review як частина Booking | Оцінка залежить від простору (Space), а не від конкретного бронювання |
| Payment напрямо від User | Платіж мав би відслідковувати період (user_membership_id), а не просто користувача |
| Space як атрибут Booking | Простір — окрема сутність, можна аналізувати незалежно від бронювань |
| Composite PK у UserMembership | Окремий PK гнучкіший для історії змін та іншого моделювання |
| UNIQUE(space_id, booking_date, start_time) для заборони перекриття | Недостатньо, не гарантує відсутність перетину часових інтервалів |

---

## Висновок

Ця ER-модель:
- ✅ Нормалізована до 3NF
- ✅ Адекватна бізнес-логіці коворкінгу
- ✅ Гнучка для розширень (нові поля, нові сутності)
- ✅ Вільна від аномалій вставлення/видалення
- ✅ Дозволяє правильний облік платежів та членств
- ✅ Правильно формулює бізнес-правила на рівні специфікації, а не как SQL обмеження
