# spec.md — Специфікація системи бронювання коворкінгу

## Сутності та атрибути

### 1. **User** (Користувач)
Представляє членів коворкінгу.

| Атрибут | Тип | Опис |
|---------|-----|------|
| user_id | INT, PK | Унікальний ідентифікатор |
| email | VARCHAR(255), UK | Email користувача (унікальний) |
| full_name | VARCHAR(255) | Повне ім'я |
| phone | VARCHAR(20) | Номер телефону |
| created_at | TIMESTAMP | Дата реєстрації |
| is_active | BOOLEAN | Статус активності |

---

### 2. **Membership** (Пакет членства)
Визначає права та обмеження користувача.

| Атрибут | Тип | Опис |
|---------|-----|------|
| membership_id | INT, PK | Унікальний ідентифікатор |
| name | VARCHAR(100) | Назва пакету (e.g. "Basic", "Pro", "Premium") |
| max_hours_per_month | INT | Максимум годин на місяць |
| price_per_month | DECIMAL(10,2) | Вартість пакету |
| created_at | TIMESTAMP | Дата створення |

---

### 3. **UserMembership** (Членство користувача)
**Асоціативна сутність** — зв'язує користувача з пакетом членства та несе власні атрибути про термін дії членства.

| Атрибут | Тип | Опис |
|---------|-----|------|
| user_membership_id | INT, PK | Унікальний ідентифікатор |
| user_id | INT, FK → User | Посилання на користувача |
| membership_id | INT, FK → Membership | Посилання на пакет |
| start_date | DATE | Дата початку членства |
| end_date | DATE | Дата закінчення членства |
| is_active | BOOLEAN | Чи активне членство |

**Обґрунтування:** UserMembership — це повноцінна сутність з власним PK та семантичним змістом. Несе атрибути `start_date`, `end_date`, `is_active`, що описують період дії конкретного членства користувача. Користувач може змінювати пакети з часом, тому кожне членство — це окремий період.

---

### 4. **Space** (Простір)
Представляє фізичні простори, доступні для бронювання.

| Атрибут | Тип | Опис |
|---------|-----|------|
| space_id | INT, PK | Унікальний ідентифікатор |
| name | VARCHAR(100) | Назва простору (e.g. "Conference Room A") |
| space_type | ENUM | Тип: 'desk', 'meeting_room', 'private_office' |
| capacity | INT | Кількість осіб |
| location | VARCHAR(100) | Розташування в будівлі |
| price_per_hour | DECIMAL(10,2) | Вартість на годину |
| is_available | BOOLEAN | Доступність |

---

### 5. **Booking** (Бронювання)
Представляє резервування простору користувачем.

| Атрибут | Тип | Опис |
|---------|-----|------|
| booking_id | INT, PK | Унікальний ідентифікатор |
| user_id | INT, FK → User | Який користувач забронював |
| space_id | INT, FK → Space | Який простір забронював |
| booking_date | DATE | Дата бронювання |
| start_time | TIME | Час початку |
| end_time | TIME | Час закінчення |
| status | ENUM | Статус: 'pending', 'confirmed', 'cancelled', 'completed' |
| created_at | TIMESTAMP | Дата створення бронювання |

**Обґрунтування:** Booking — асоціативна сутність, що зв'язує User і Space. Несе власні атрибути (дата, час, статус), тому потребує окремої сутності замість прямого зв'язку User→Space.

---

### 6. **Payment** (Платіж)
Відстежує платежі користувачів за членства.

| Атрибут | Тип | Опис |
|---------|-----|------|
| payment_id | INT, PK | Унікальний ідентифікатор |
| user_membership_id | INT, FK → UserMembership | Членство, за яке платіж |
| amount | DECIMAL(10,2) | Сума платежу |
| payment_date | TIMESTAMP | Дата платежу |
| payment_method | ENUM | Спосіб: 'card', 'bank_transfer', 'cash' |
| status | ENUM | Статус: 'pending', 'completed', 'failed' |

---

### 7. **Review** (Оцінка/Коментар)
Дозволяє користувачам оцінювати простори після використання.

| Атрибут | Тип | Опис |
|---------|-----|------|
| review_id | INT, PK | Унікальний ідентифікатор |
| user_id | INT, FK → User | Хто залишив оцінку |
| space_id | INT, FK → Space | Який простір оцінюється |
| rating | INT | Оцінка від 1 до 5 |
| comment | TEXT | Текст коментаря |
| created_at | TIMESTAMP | Дата оцінки |

**Обґрунтування:** Review — асоціативна сутність, що зв'язує User і Space. Несе власні атрибути (рейтинг, коментар), тому потребує окремої сутності замість прямого зв'язку User→Space.

---

## Зв'язки між сутностями

| Сутність 1 | Зв'язок | Сутність 2 | Кардинальність | Опис |
|-----------|--------|-----------|---------------|----|
| User | має | UserMembership | 1:M | Один користувач може мати кілька послідовних членств (змінювати пакети) |
| Membership | використовується у | UserMembership | 1:M | Один пакет членства може бути використаний багатьма користувачами |
| UserMembership | генерує | Payment | 1:M | Одне членство може мати кілька платежів |
| User | створює | Booking | 1:M | Один користувач може створити багато бронювань |
| Space | отримує | Booking | 1:M | Один простір може мати багато бронювань |
| User | пише | Review | 1:M | Один користувач може залишити багато відгуків про різні простори |
| Space | отримує | Review | 1:M | Один простір може отримати багато відгуків від різних користувачів |

**Важливо:** Взаємодія User ↔ Space реалізується опосередковано через асоціативні сутності Booking та Review. Прямого зв'язку User→Space в моделі немає.

---

## Критерії нормалізації (3NF)

1. **1NF (Atomic Values)**: Усі атрибути містять атомарні значення
2. **2NF (Partial Dependencies)**: Всі неключові атрибути залежать від повного первинного ключа
3. **3NF (Transitive Dependencies)**: Немає перехідних залежностей

### Нормалізація по сутностях:

- **User**: ✅ 3NF — атомарні поля, всі залежать від user_id
- **Membership**: ✅ 3NF — всі атрибути залежать від membership_id
- **UserMembership**: ✅ 3NF — всі атрибути залежать від user_membership_id
- **Space**: ✅ 3NF — атомарні поля, всі залежать від space_id
- **Booking**: ✅ 3NF — дати/часи атомарні, залежать від booking_id
- **Payment**: ✅ 3NF — залежить від user_membership_id; без перехідних залежностей
- **Review**: ✅ 3NF — залежить від review_id; всі атрибути атомарні

### Зовнішні ключі (FK):
- UserMembership.user_id → User.user_id
- UserMembership.membership_id → Membership.membership_id

- Booking.space_id → Space.space_id

- Review.user_id → User.user_id
- Review.space_id → Space.space_id

## Додаткові бізнес-правила

1. **Активне членство:** Користувач може мати лише одне активне членство на раз (`is_active = true` в UserMembership)

2. **Відсутність перекриття бронювань:** Для одного простору два активні бронювання в один день не можуть мати часові інтервали, що перетинаються. Два бронювання конфліктують, якщо їхні інтервали (start_time, end_time) мають спільні точки.
   - **Приклад конфлікту:**
     - Booking A: 10:00–12:00
     - Booking B: 11:00–13:00
     - **Результат:** Конфлікт (перекриття з 11:00 до 12:00)
   - **Реалізація:** Перевірка в прикладному коді перед вставкою/оновленням

3. **Членство потребує активності:** Користувач не може забронювати простір, якщо його членство неактивне (бізнес-логіка в додатку)

4. **Платіж пов'язаний з членством:** Платіж пов'язаний з членством (user_membership_id), не з окремими бронюваннями. Один платіж охоплює весь період членства.

5. **Оцінка після завершення:** Оцінка (Review) може залишатися лише після завершеного бронювання (status = 'completed')

## Допущення

- Один простір може бути зареєстрований у системі один раз
- Час бронювання виражається у форматі HH:MM (24-годинна система)
- Рейтинг коливається від 1 до 5
- Грошові суми позначені як DECIMAL(10,2) для точності
- Системні часові мітки зберігаються в UTC (TIMESTAMP)
- Перевірка неперекриття бронювань здійснюється на прикладному рівні (в бізнес-логіці додатку)

## Походження моделі

Ця модель розроблена для системи управління коворкінгом:
- Керування користувачами та їх членствами
- Планування та бронювання просторів без перекриття
- Отримання платежів за членства
- Збирання відгуків про якість просторів
